# Engineering Session Log: Centralized Logging Deployment & Troubleshooting

Date: May 17, 2026

Infrastructure State: Multi-node local simulation (Node 1: Control, Node 2: Target, Node 3: Log Receiver)
Phase 1: Code Management & Git Diagnostics

The session began with an attempt to stage local configuration files, which triggered a repository error.

    Symptom: Running git add . returned fatal: not a git repository.

    Diagnosis: The local directory home-lab-docs was uninitialized and lacked a .git tracking folder.

    Resolution:

        Initialized the local workspace: git init

        Verified that the .gitignore file was successfully masking hidden or private credential files using git status.

        Staged and committed the documentation locally.

        Linked the local workspace to a newly created, empty public GitHub repository and pushed the main branch live.

Phase 2: Ansible Privilege Escalation Triage

With version control established, attention turned to automating system baselines from Node 1 to the target environment.

    Symptom: Running the baseline playbook resulted in a timeout error during the initial facts gathering phase:
    fatal: [node2]: UNREACHABLE! => {"msg": "Task failed: Timeout (12s) waiting for privilege escalation prompt:"}

    Diagnosis: The managed target nodes (node2 and node3) requested a sudo password validation that the non-interactive Ansible SSH session could not pass through automatically using default parameters.

    Resolution: Updated the central inventory file (hosts) on Node 1 to explicitly pass privilege variables down to the target group:
    [targets:vars]
    ansible_become_method=sudo
    ansible_become_ask_pass=True

    Result: Re-running the playbook passed successfully with ok=3 across all targets, validating the underlying SSH trust mesh.

Phase 3: Rsyslog Receiver Configuration (Node 3)

To transition from individual machine management to centralized monitoring, Node 3 was configured as a central syslog collector.

    Configuration:

        Created a standard system backup of the live configuration file using the [filename].[YYYYMMDD].bak rule.

        Opened /etc/rsyslog.conf and enabled UDP/TCP module drivers on network port 514.

        Implemented a dynamic routing storage template to automatically sort incoming logs into isolated folders based on the source hostname:
        $template RemoteLogs,"/var/log/nodes/%HOSTNAME%/%PROGRAMNAME%.log"
        . ?RemoteLogs
        & stop

    Verification: Restarted the service and verified socket status using ss -tulnp | grep 514, confirming the daemon was listening globally.

Phase 4: Pipeline Troubleshooting & Socket Activation

Forwarding configuration files (60-remotelog.conf) were deployed to Node 1 and Node 2 directing them to ship data to Node 3 (@@192.168.26.133:514). However, no remote data was appearing in the collection directory.
Diagnostic Step A: Permissive Block

    Symptom: Running ls -l /var/log/nodes/ returned No such file or directory.

    Diagnosis: The default syslog user account did not have directory-write privileges under the root /var/log/ path to spin up the parent folder on the fly.

    Resolution: Manually initialized the directory and adjusted explicit group ownership:
    sudo mkdir -p /var/log/nodes
    sudo chown -R syslog:adm /var/log/nodes

Diagnostic Step B: Rule Ingestion Priority

    Symptom: The directory existed, but running ls -l returned total 0. Only Node 3 logged to itself.

    Diagnosis: The custom routing template was placed at the bottom of the configuration file. Default upstream rules processed and discarded the log packets before they reached the template block.

    Resolution: Shifted the $template block to the absolute top of /etc/rsyslog.conf, placing it directly below the network input bindings to grant it execution priority.

Diagnostic Step C: Systemd Socket Handshake Failure

    Symptom: Node 1 status profiles reported persistent I/O exceptions:
    rsyslogd: omfwd: target 192.168.26.133:514 became unavailable... no working target servers

    Diagnosis: Attempting to run sudo systemctl stop rsyslog threw a warning that syslog.socket remained active. Ubuntu's modern systemd socket activation mechanism was keeping the background network pipe open, trapping the application layer in a corrupted, suspended connection loop.

    Resolution: Executed a synchronized hard reset of both the tracking socket and the logging daemon concurrently on the client nodes:
    sudo systemctl stop rsyslog syslog.socket
    sudo systemctl start syslog.socket rsyslog

Final Verification & Definition of Done

Following the systemd socket lifecycle purge, a manual event blast was initiated from Node 1 (logger -p user.err "POST_RESET...").

    Final Output Status: Running ls -l /var/log/nodes/ on Node 3 returned a populated tracking directory structure, confirming that remote logs from lab-node-1 and node2 are successfully streaming across the virtual network and parsing onto disk in real time.
